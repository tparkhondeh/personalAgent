# راهنمای دائمی ساخت و تحویل Android

این سند حاصل خطاهایی است که هنگام ساخت نسخه Android پروژه «همراه» رخ داد. هدف آن این است که صفحه سفید، لینک منقضی، اشتباه‌گرفتن APKها و اعلام موفقیت زودهنگام دوباره تکرار نشوند.

## نسخه مرجع تأییدشده

- نام روی گوشی: `همراه پایدار 14`
- Package ID: `ir.wealthos.personalagent.stable14`
- فایل: `Hamrah-stable-14.apk`
- Commit سازنده: `e26a8f044aeef874a4adda66c9adb2f3f456cb14`
- SHA-256: `b3ef3b0ce07632565a2e5db2216d0ffc7da560a8c31dc9368342c1cfb9e17e32`
- نتیجه: Android 13، 14 و 16 در شبیه‌ساز موفق؛ بازشدن برنامه روی گوشی واقعی نیز در ۲۰۲۶-۰۹-۰۵ توسط مالک تأیید شد.

## علت‌های اصلی خطا و راه‌حل دائمی

### ۱. لینک موقت داخل APK

نسخه‌های قدیمی به Pinggy یا Tunnel موقت متصل بودند. با منقضی‌شدن آدرس، برنامه خطای `ERR_NAME_NOT_RESOLVED` یا صفحه سفید نشان می‌داد.

قانون دائمی:

- هیچ APK قابل تحویل نباید به Pinggy، Cloudflare Quick Tunnel، localhost.run یا آدرس رایگان و موقت وابسته باشد.
- نسخه متصل فقط از Staging پایدار HTTPS یا Production تأییدشده استفاده می‌کند.
- رابط محلیِ داخل APK باید حتی بدون سرور قابل نمایش باشد.

### ۲. سفیدماندن WebView هنگام خطای شبکه

نمایش صرف WebView کافی نبود. برای شروع برنامه Loading بومی، Timeout بیست‌ثانیه‌ای، تشخیص محتوای خالی، مدیریت خطای بارگذاری، توقف SSL نامعتبر و صفحه بازیابی فارسی اضافه شد.

قانون دائمی:

- خطای SSL هرگز نادیده گرفته نمی‌شود؛ اتصال لغو و صفحه امن بازیابی نمایش داده می‌شود.
- خطاهای شبکه، JavaScript و Renderer ثبت می‌شوند، اما اطلاعات محرمانه به کاربر نشان داده نمی‌شود.
- صفحه بازیابی باید دکمه‌های «تلاش دوباره» و «ادامه در حالت محلی» داشته باشد.
- تغییر مقصد باید کش، Cookie، Web Storage و Service Worker قدیمی را بی‌اثر کند.

### ۳. نامطمئن‌بودن بازکردن فایل محلی

در بعضی نسخه‌های Android WebView، رفتن مستقیم از صفحه بازیابی به `https://localhost/index.html` یا دریافت `./index.html` با `fetch()` شکست خورد؛ هرچند همان مسیر در مرورگر دسکتاپ سالم بود.

راه‌حل دائمی:

- `scripts/generate-android-assets.mjs` رابط محلی، CSS و JavaScript را هنگام Build مستقیماً داخل `mobile-shell/connection-error.html` جاسازی می‌کند.
- صفحه محلی با `document.open/write/close` باز می‌شود و به Navigation یا Fetch وابسته نیست.
- `pnpm android:sync` باید همیشه Generator را پیش از Capacitor Sync اجرا کند.

### ۴. خراب‌شدن JavaScript در Generator

استفاده از متن جایگزین در `String.replace` باعث شد علامت‌های `$` و `$$` در JavaScript تغییر کنند و خطای `Identifier '$' has already been declared` ایجاد شود.

قانون دائمی:

- برای قراردادن HTML، CSS یا JavaScript دلخواه در خروجی تولیدشده، `String.replace(regex, callback)` استفاده شود؛ نه Replacement String.
- تولید Asset باید دوبارپذیر باشد و اجرای دوباره آن خروجی را خراب نکند.
- کد جاسازی‌شده پیش از Build از نظر Syntax و حضور متن واقعی فارسی آزمایش شود.

### ۵. اشتباه‌شدن نسخه قدیمی و جدید

چند APK با نام ظاهری مشابه باعث شد تشخیص نسخه نصب‌شده دشوار شود.

قانون دائمی:

- هر نسخه آزمایشی مهم باید نام برنامه، Package ID، Version Code و نام فایل منحصربه‌فرد داشته باشد.
- همراه Release باید `metadata.json` و `SHA256SUMS.txt` منتشر شود.
- نام برنامه، Package ID، Commit، SHA-256 و لینک Release باید هنگام تحویل اعلام شوند.
- نسخه‌های Pinggy و Tunnel قدیمی منسوخ‌اند و نباید دوباره پیشنهاد یا نصب شوند.

### ۶. تست ناکافی

بازبودن Process یا متفاوت‌بودن رنگ Screenshot با سفید، اثبات سلامت رابط نبود.

قانون دائمی:

- همان فایل APK که تحویل می‌شود فقط یک‌بار در CI ساخته و در تمام آزمایش‌ها استفاده شود.
- روی Android 13، 14 و 16 نصب و Cold Launch شود.
- متن واقعی فارسی و RTL با WebView/CDP بررسی شود.
- Screenshot صفحه واقعی ورود، بازیابی یا داشبورد ذخیره و بصری کنترل شود.
- اینترنت سالم، اینترنت قطع، DNS خراب، سرور خاموش، SSL نامعتبر و اجرای دوباره برنامه آزمایش شوند.
- Logcat از نظر Crash، خطای JavaScript، شبکه و WebView بررسی شود.
- اعلان دارای صدا، Alarm دقیق و لغو Alarm با تست رفتاری کنترل شوند.
- Release فقط پس از موفقیت تمام Jobهای اجباری منتشر شود.

نکته: Android 14 یک بار پس از Force Stopهای سریع با توقف گذرای Emulator روبه‌رو شد. اجرای دوباره همان APK بدون تغییر کد موفق بود. در چنین وضعی ابتدا همان Artifact دوباره آزمایش می‌شود تا خطای زیرساخت با خطای برنامه اشتباه نشود؛ هیچ کنترل اجباری حذف یا ضعیف نمی‌شود.

### ۷. نام فایل‌های مدرک

Screenshotهای چند نسخه Android اگر نام یکسان داشته باشند، هنگام انتشار با هم تداخل می‌کنند.

قانون دائمی:

- API Level باید در نام Screenshot، Log و Artifact نوشته شود.
- تمام مدارک هر اجرا با شماره Run و Commit قابل ردیابی باشند.

## چک‌لیست اجباری پیش از تحویل APK

- Commit لوکال، `BUILD_COMMIT.txt` و `/api/health` سرور، و `metadata.json` APK باید جداگانه تطبیق داده شوند. Push کد به‌تنهایی Staging یا APK را به‌روز نمی‌کند.
- آزمون رابط آفلاین باید علاوه بر متن فارسی، شعر ۳۶۰تایی، تاریخ میلادی، ایجاد سه اعلان بومی و لغو آن‌ها بعد از تکمیل کار را بررسی کند.
- ساخت بسته Linux هم‌نسخه با APK در Workflow پایدار انجام می‌شود. ارتقای Staging فقط با `scripts/deploy-staging-release.sh`، بررسی Hash و Backup انجام شود؛ بازگشت به Release قبلی داده‌های جدید کاربر را بازنویسی نمی‌کند.

- [ ] در خطای شبکه، DNS، SSL یا سرور صفحه سفید دیده نمی‌شود.
- [ ] APK تحویلی همان Artifact آزمایش‌شده است و دوباره Build نشده است.
- [ ] نام برنامه، Package ID، Version، Commit و SHA-256 ثبت شده‌اند.
- [ ] Android 13، 14 و 16 با متن واقعی فارسی و RTL موفق‌اند.
- [ ] Screenshot و Logcat واقعی بررسی شده‌اند.
- [ ] Type Check، Lint، Test، Build، Android Lint و تست‌های Android موفق‌اند.
- [ ] فایل محیطی، Secret، Keystore یا کلید امضا وارد Git نشده است.
- [ ] APK روی گوشی واقعی نصب و بازشدن آن ثبت شده است، یا این مورد صریحاً «معوق» اعلام شده است.
- [ ] Production و دامنه اصلی بدون تأیید نهایی مالک تغییر نکرده‌اند.

## Staging، Backup و Rollback

- Staging فعلی روی `https://personalagent.wealthos.ir:8443` از Production جداست.
- پیش از هر تغییر سرور، از دیتابیس، تنظیمات، Release فعال و وضعیت Processها Backup گرفته می‌شود.
- تغییر Production فقط با تأیید نهایی مالک انجام می‌شود.
- اگر GitHub Runner به پورت Staging دسترسی نداشت، تست رابط محلی و Recovery در Runner ادامه پیدا می‌کند و Smoke Test سرور جداگانه انجام می‌شود؛ بررسی‌ها حذف نمی‌شوند.

## خطاهای کشف‌شده در آزمون همسانی نسخه ۱۵ (۲۰۲۶-۰۹-۰۶ UTC)

- آزمون واقعی سه یادآوری روی هر سه Android شکست خورد: `Native notification bridge missing`. بازشدن رابط به‌تنهایی اثبات کارکرد اعلان نیست؛ نسخه ۱۵ منتشر نشد.
- Capacitor 8.5 صفحه `errorPath` را بدون تزریق پل افزونه‌ها تحویل می‌دهد؛ همچنین اسکریپت شروع سند در حالت متصل فقط برای مبدأ سرور فعال است. `MainActivity` پل استاندارد خود Capacitor را فقط در سند اصلیِ بازیابیِ داخل APK و فقط برای `LocalNotifications` تزریق می‌کند. مبدأها، اعتبارسنجی SSL و مجوزهای سیستم‌عامل تغییر نمی‌کنند.
- فونت باید از فایل داخل APK در مبدأ خصوصی `localhost` خوانده شود؛ مسیر دقیق فونت توسط برنامه سرو می‌شود. آزمون واقعی بارگیری Vazirmatn نیز الزامی است.
- آزمون باید سه اعلان بومی آینده را از فرم واقعی ایجاد کند، در `getPending` ببیند و پس از تکمیل کار لغوشدن آن‌ها را اثبات کند. این کنترل را برای سبزشدن CI حذف نکنید.
- کلید عمومی Web Push اکنون از API احرازهویت‌شده و در زمان اجرای سرور دریافت می‌شود؛ اتصال اعلان نباید به وجود تنظیمات Staging هنگام Build در GitHub وابسته باشد. کلید خصوصی فقط در سرور می‌ماند.
- آزمون نسخه ۱۶ نشان داد `String.replace` در Java تمام `<head>`ها، حتی نمونه داخل رشته JSON رابط جاسازی‌شده، را تغییر می‌دهد و SyntaxError ایجاد می‌کند. درج اسکریپت اکنون با برش در نخستین head واقعی انجام می‌شود؛ تست واحد، دست‌نخورده‌ماندن رشته HTML داخلی و `$` و backslash را کنترل می‌کند. نسخه ۱۶ منتشر نشد.
- نسخه ۱۷ دیگر SyntaxError نداشت، اما تست بارگیری فونت، NetworkError پیدا کرد. برخلاف نام متد، `Bridge.getLocalUrl()` در حالت متصل به مبدأ سرور اشاره می‌کند، نه `localhost`. مبدأ منابع داخل APK اکنون از `getScheme()` و `getHost()` ساخته می‌شود. این تفاوت باید در هر تغییر Capacitor بررسی شود؛ فونت خارج از APK یا نادیده‌گرفتن آزمون راه‌حل نیست. نسخه ۱۷ منتشر نشد.

## امنیت انتشار

- در آزمون نسخه ۱۸، Android 13 و 16 کامل موفق شدند؛ Android 14 پس از موفقیت فونت و سه اعلان، به‌علت مرگ `com.google.android.gms.persistent` بسته شد. Logcat صریحاً `depends on provider ... FontsProvider in dying proc` را ثبت کرد. این رخداد شبیه‌ساز را با خطای JavaScript برنامه اشتباه نگیرید؛ لاگ را نگه دارید و همان APK را دوباره آزمایش کنید. حذف آزمون آفلاین یا اعلان برای سبزشدن نتیجه مجاز نیست. تا موفقیت هر سه Android، نسخه قابل تحویل نیست.

- APK فعلی آزمایشی و Debug-signed است.
- Keystore، رمز امضا، `.env`، کلید API و اطلاعات شخصی هرگز وارد Git یا Artifact عمومی نمی‌شوند.
- پیامک و تماس تا انتخاب سرویس‌دهنده، شماره تأییدشده و تأیید هزینه در حالت Mock می‌مانند.
- محدودیت‌های Android، SSL، احراز هویت یا محدودیت کشوری دور زده نمی‌شوند.
