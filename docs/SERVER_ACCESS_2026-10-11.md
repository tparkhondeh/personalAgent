# درخواست بررسی مسیر اتصال tia — ۱۱ اکتبر ۲۰۲۶

این گزارش فقط تشخیص خواندنی است؛ تنظیمات سرور، دامنه، TLS، حساب، داده و هزینه تغییر نکرده‌اند.

## خلاصهٔ تازه برای ارسال

«از ویندوز توسعه، اتصال به `personalagent.wealthos.ir` روی پورت‌های `443` و `8443` در مرحلهٔ TLS متوقف می‌شود؛ نمونهٔ تازه:۱۱اکتبر۲۰۲۶، ساعت۱۷:۴۱تهران. اتصال SSH به `62.204.61.18:2490` نیز پیش از ورود، در تبادل کلید متوقف شده است. مسیر ویندوز از `singbox_tun` عبور می‌کند. لطفاً مدیر همین ویندوز/شبکه وضعیت تونل و MTU/MSS و مدیر سرور لاگ‌های فایروال، TLS/SNI و SSH را بررسی کنند؛ بازبودن پورت کافی نیست. علت هنوز قطعی نیست. فعلاً رمز، DNS، مقصد برنامه یا تنظیمات امنیتی مشترک را تغییر ندهید و TLS را دور نزنید.»

همان۱۱اکتبر، نسخهٔ نهایی امضاشده۴۵ از GitHub روی اندروید۱۳/۱۴/۱۶ صفحهٔ واقعی۸۴۴۳ را در شروع و پایان باز کرد. پس خرابی همگانی سرور یا خرابی قطعی CDN اثبات نشده؛ رسیدن به صفحه نیز اثبات اتصال فعلی GPT نیست. برنامهٔ جدید منتشر شده، اما بستهٔ وب تازه نصب سرور نشده است.

## متن قابل ارسال برای مدیر سرور/شبکه

از محیط Windows توسعه، اتصال به `personalagent.wealthos.ir` کامل نمی‌شود. لطفاً مسیر همین مبدأ را بررسی کنید، نه اینکه صرفاً بازبودن پورت را تأیید کنید:

1. ساعت **۱۴:۰۴:۵۰ تهران، ۱۱ اکتبر ۲۰۲۶** (10:34:50 UTC)، اتصال TCP به IP `185.226.140.40` روی هر دو پورت **443 و 8443** برقرار شد، اما TLS در۱۰ثانیه کامل نشد. HTTP پاسخی نداده؛ خطای404 یا گواهی نامعتبر مشاهده نشده است. DNS دو IPv4 یعنی `185.226.140.40` و `185.226.142.42` برگرداند؛ این نمونهٔ تازه فقط IP اول را انتخاب کرد.
2. روی SSH موجود `62.204.61.18:2490`، TCP و بنر `OpenSSH_8.0` دریافت می‌شود. در10:32:13 UTC تبادل `KEXINIT` انجام شد و الگوریتم `curve25519-sha256` انتخاب شد، اما کلاینت در انتظار `SSH2_MSG_KEX_ECDH_REPLY` ماند و مهلت۱۸ثانیه تمام شد؛ هنوز پذیرش/رد کلید ورود رخ نداده است. بررسی رمز یا ساخت کلید تازه قدم اول نیست.
3. بررسی خواندنی مسیر ویندوز نشان می‌دهد ترافیک هر دو مقصد HTTPS و SSH از رابط **`singbox_tun` با IP خصوصی172.18.0.1 و NextHop172.18.0.2** عبور می‌کند؛ این مسیر Ethernet مستقیم نیست. ابتدا مدیر همین ویندوز/شبکه، مسیر و وضعیت تونل را بررسی کند. مدیر سرور نیز در زمان‌های بالا لاگ فایروال/ACL، محدودیت IP مبدأ، TLS/SNI همین زیردامنه و SSH را بررسی کند؛ اگر درخواست به مقصد نمی‌رسد، تغییر برنامه یا Nginx قدم اول نیست. MTU، CDN و تونل فقط مظنون‌اند، نه علت قطعی. IP خروجی عمومی باید از لاگ شبکه/درگاه NAT مشخص شود.
4. درخواست: HTTPS معتبر با نام دقیق همین زیردامنه روی443/8443 و SSH موجود بدون تغییر مقصد/شناسه/کلید دوباره از همین کلاینت قابل استفاده شوند. TLS را دور نزنید و تنظیمات مشترک `wealthos.ir` یا سایر پروژه‌ها را تغییر ندهید. اگر تغییر لازم شد، هدف دقیق، اثر و روش بازگشت را پیش از اجرا مشخص کنید.

صفحه Staging در آزمون۱۰اکتبر از GitHub با TLS عادی باز شده بود؛ بنابراین این شواهد خرابی عمومی سرور را ثابت نمی‌کنند. ممکن است مسیر همین کلاینت یا سیاست وابسته به مبدأ دخیل باشد. سیاست کش بعد از برقراری TLS/HTTP بررسی می‌شود؛ پاک‌کردن کش/کوکی یا داده کاربر این آزمایش را اصلاح نمی‌کند.
